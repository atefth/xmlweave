# Scope decisions after the XML toolkit roadmap

Issue #29 asks for explicit decisions, not automatic implementation of every Java XML ecosystem feature. The parser, XPath, event streaming, self-contained XSD validation and constrained transformations form the current toolkit scope. The following assessments record a separate decision for each adjacent capability.

| Capability | User need and cost | Decision and prerequisites |
| --- | --- | --- |
| XML signatures | Needed for signed business documents or identity protocols. Requires canonicalization variants, algorithm/key policy, wrapping-attack resistance, certificate trust and interoperability vectors; ordinary serialization is not canonicalization. | Defer. There is no concrete signing protocol or trust policy in the current requirements. Require a target signature profile, audited crypto dependency, threat model and independent security/interoperability review before creating implementation stories. |
| SOAP | Needed for a specific SOAP service contract, including version, HTTP binding, envelopes, faults and potentially WS-* security. A generic XML parser does not provide transport/retry/authentication semantics. | Defer. Require real WSDLs, SOAP version, authentication, transport and fault-handling requirements. A service-specific adapter can be assessed once a concrete integration exists. |
| JAXB-style binding | Needed when schema-generated types and generated serializers are preferable to explicit DOM operations. Requires namespace/type mapping, code generation strategy, optionality, polymorphism and schema evolution decisions. | Defer. Require sample XSDs/documents, generation/runtime footprint goals and explicit roundtrip expectations before choosing a binding model. |
| Object mapping | Useful for a small data shape, but a universal object conversion can lose mixed content order, namespaces, attributes and lexical distinctions. | Defer a general mapper. Current explicit DOM methods and XPath extraction cover known needs. Require a written mapping contract and representative roundtrip fixtures before implementing an optional adapter. |

These decisions do not block or diminish the implemented toolkit. They keep cryptographic and protocol claims outside the supported API until concrete requirements exist. No implementation follow-up is opened because no inclusion decision has been made; future demand should supply the prerequisites above and lead to a new scoped story. Closing #29 means this decision record and assessment are complete, not that signatures, SOAP or binding have been implemented.
